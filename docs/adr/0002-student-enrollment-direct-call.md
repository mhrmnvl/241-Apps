# Student enrollment: direct synchronous call instead of a domain event

**Context**: "assign a student to a classroom, ensuring an enrollment exists" was implemented twice, independently: `CreateStudentUseCase` emits a `student.created` event after creating a student with a `classroomId`; `ResolveBulkImportConflictsUseCase`'s update branch does its own "already enrolled?" check and emits the same event on conflict resolution. Both emissions are fire-and-forget — `EventEmitter2.emit(...)` is never awaited, so `StudentEventListener.handleStudentCreated` (the event's only listener, in `EnrollmentModule`) runs after the caller has already returned a response. If enrollment creation fails there (no active semester, a DB constraint, ...), the failure is only logged — it never reaches the API response or the bulk-import row's `errors[]`, so a bulk-import row (or a student create) can report success while the student ends up unenrolled.

**Decision**: replace both emit sites with a direct, awaited call to a new `EnsureStudentEnrollmentUseCase`, registered in and exported from `EnrollmentModule`. `StudentModule` now imports `EnrollmentModule` to inject it. The use-case is self-contained and idempotent — callers pass only `studentId` and `classroomId`; it checks current enrollment state itself via `IEnrollmentRepository` and resolves the active semester internally, matching the listener's prior behavior. `StudentCreatedEvent` and `StudentEventListener` are deleted, along with their registration in `EnrollmentModule` — the event had exactly one listener and two emitters, all being replaced.

**Why not keep the event**: `student` and `enrollment` were kept deliberately decoupled via this event (`EnrollmentModule` does not import `StudentModule`, only a type-level import of the event class). That decoupling traded away correctness: an operation whose success is part of what "creating/resolving a student" means was allowed to fail silently after the response was already sent. `EnrollmentModule` already exports `IEnrollmentRepository` for external consumption, and the new dependency (`student → enrollment`) is one-directional, not circular. Domain events remain the right tool for genuine fan-out (multiple independent subscribers reacting to a fact) — this was never that; it was a 1:1 relationship between one business rule and one consequence, better served by a direct, awaited call whose errors propagate into the existing per-row `try/catch` in `ResolveBulkImportConflictsUseCase` and into `CreateStudentUseCase`'s response.

## Considered Options

- Keep the event, move the "already enrolled" check into a shared use-case that still emits (fire-and-forget) — rejected: deduplicates the check but keeps the silent-failure gap that motivated this change.
- Have the new use-case query enrollment state via `IEnrollmentRepository` but keep two separate emit call sites (no shared use-case) — rejected: still duplicates the "resolve classroom, decide, act" shape across `create-student` and `resolve-bulk-import-conflicts`.

## Consequences

- `student` now has a compile-time dependency on `enrollment` (one new module edge, not circular). Future cross-domain rules with a single, must-succeed consequence should default to a direct awaited call, not an event — reserve domain events in this codebase for genuine multi-subscriber fan-out.
- Enrollment failures during student creation or bulk-import conflict resolution now surface as real errors (in `CreateStudentUseCase`'s response chain, and in `ResolveBulkImportConflictsUseCase`'s per-row `errors[]`) instead of being silently logged.
